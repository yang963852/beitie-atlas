### A · 文献 Agent 的任务卡

固定两份研究提交，按下表只读查阅旧档、研究 JSON 和原始著录。每条结论登记 **作品号、实物或事件号、说法、提出者、直接来源／转引、段落定位、实际访问日期、核对结果、未决点**。同一网页的两跋分别登记。网页打不开时写明哪条说法受影响，可继续其余条目。两篇只核到摘要的研究须保留查阅层级；如取得全文，注明具体新增依据和页码。

| --- | --- | --- |
| 颜勤礼碑 · `yan-qinli-original-stele`、`dpm-rubbing-xin00045406` | 对照原石事件与新00045406 的馆藏段；写明拓本制作期能精确到什么程度 | 把原石出土史交给民国拓本；凭作品相同指定底石 |

### B · 数据 Agent 的任务卡

1. 读取固定版本的试例。查 `src/domain/types.ts`、`src/domain/knowledge-types.ts`、`src/domain/validate.ts`、`scripts/lib/knowledge-schema.ts`、`scripts/lib/knowledge-compiler.ts`，列出哪些信息旧档已有、哪些仅在研究层。旧字段及审核状态以仓库源文件为准。
2. 在独立研究目录实现最小的只读校验，可使用 Node 和已有依赖。输入为试例及对应提交的源档；输出以作品／实物／断言号报告成功或错误。若 #34 尚未合并，可以在项目私有临时目录读取固定版本；在持久交付中给出输入提交号和重现命令。研究脚本由 B 维护，A 独立维护证据表。
3. 检查 ID 唯一、引用存在、事件属于正确实物、版本与实物同作、图像绑定本件、每条断言有说话者和段落、冲突组的成员和值均可复原。用仅供测试的副本分别制造坏出处、错绑实物、缺定位和冲突成员遗失。每个坏例都应失败并指出哪一条，恢复后通过。
4. 按原研究 Q1–Q10 交付“问题／输入号／实际结果／出处／未知项”。验证祭侄两种年份可分别检出、神龙本同一归名的支持与质疑均能返回。对照旧格式的馆号、生产年代、事件、双语原文和审核状态；解释旧字段无法表示的细节。报告本轮实际覆盖数量及未覆盖类型。
5. 交接时给出可直接执行的一行研究校验命令、结果及复现所需版本；注明哪些是程序验证，哪些仍依赖 A 的史料判断。生产加载器、地图和出版门槛不在本卡改动范围。

### C · 性能 Agent 的任务卡（可与 A、B 并行）

以同一提交构建预览，分别测首页进入时间轴、直接打开 `#/object/witness-jizhi`、搜索实物、打开馆藏地图。记录设备、浏览器、网络、缓存状态、次数和结果。建议每条路径做三次冷启动并列出原始值及中位数；保留首次可读正文的判定方法。区分首屏实际传输量与构建工具的 gzip 估算。没有真机则注明模拟条件；测不出大陆公网可达性时留空。有无地图键、直接进入正文和加载 Three.js 开场的结果分别记录。交付测量表和一项最值得继续测的瓶颈；数据分包、索引改造或引入服务另行决策。

### D · 评审 Agent 与负责人的决策

评审者从原始著录重新查《祭侄文稿》两跋，复核其余三类高风险断言：实体归错、意见写成定论、年代或地点精度被提高。用 B 提供的命令重跑正常样例和反例，检查 Git 差异及输入提交。无法独立复核的材料逐条列为缺口。项目约定 P1 阻断发布，P2 在本轮修复，P3 可后续处理。研究结论与工程校验分别评价，记录 changes-required、partially-verified 或 accepted，并写明评审者。实施者自查只能标记为自审。

决策单交一页即可：**答得更好的问题及实例、仍答不了的问题、每件实际复核耗时、兼容损失、待负责人决定的一件事**。证据不足就缩小试点或继续补证；如现有注记已满足需要，可停在研究层。两件网页试点的建议对象是《祭侄文稿》和《兰亭序》，分别检验异年、归名立场两种不同的阅读需求。

### E · 网页 Agent 的有条件任务卡

负责人明确同意试点后，把已通过 D 的两件研究输入以可撤回方式接入预览。先确定谁维护唯一原稿、怎样从该稿生成只读视图，并确认公开展示的文字范围。前端使用现有 React/TypeScript/Vite 和项目设计系统，复用 `src/components/ObjectDetail.tsx`、`ProvenanceEvents.tsx`、`SourceList.tsx` 与双语机制。具体触及哪些组件以代码实际路径和页面入口为准。正文先回答“有哪几种说法”，展开后才显示提出者、出处和定位。未参与试点的条目走原阅读路径。

验收时直接打开并刷新两件实物旧链接；在手机和键盘上展开出处、返回列表；处理缺翻译、无图、无坐标、地图键缺失及加载失败。按项目规则检查 390／768／1440 像素和 200% 缩放，给出截图及操作结果。复核 GitHub 知识目录和网页指向同一来源。试点添加的读者数据须有适用的构建期检查；未经编辑批准的记录只进带草稿标识的预览，正式构建不能收录。回退试点 PR 后，旧网址、源数据、原目录和构建应仍可用。

### F · 扩样、迁移与技术选型

先由负责人圈定下一批材料与维护人，优先补五件试例没有覆盖的摩崖、残片、无坐标、无图权、机构与馆址分离等情况。用同一套问题比较旧档与新表达，逐条列出新增信息、不可逆的转换、人工工时和回退所需步骤。保留旧 ID 与分享链接。确认每个字段的权威来源后再讨论写入切换；任何丢出处、混合不同实物或升高审核状态的转换都应退回修订。

| 后续需求 | 先做的小试验 | 何时值得提交新的技术决策 |
| --- | --- | --- |
| 条目增长、跨库搜索 | 按 C 卡实测，用静态摘要、详情分包或预生成索引比较同一组查询 | 目标手机和约定数据量上仍超出负责人认可的等待时间或内存预算 |
| 高清辨字与图像标注 | 用一张权利清楚的图，从文字定位进入馆方图或已有 IIIF 画布 | 局部放大确实解决读者问题，且有批量授权原图、持续费用和维护人 |
| 多层知识关系 | 先用现有文件回答具名且有来源的两三跳问题 | 记录查询样本、耗时和失败原因，静态办法达不到约定目标时再比较图数据库 |
| 多人编辑与在线写入 | 先按作品分工、小 PR 审稿，记录冲突和等待；区分操作难与审稿慢 | 反复出现私有草稿、细粒度权限或同时编辑同一段的硬需求，再比较托管编辑或写入服务 |

新方案按 ADR 记录“问题、现状与备选、证据、代价、决定人、验证方式、回退条件”。现行部署仍以 GitHub Pages 为唯一站点。正式出版、全库迁移和新增付费服务各自立项。[工程计划](engineering-plan.md) · [发布手册](release.md)

## 交付检查与可复制派工词

研究卡交证据表、研究校验和复核结果；文档变更至少检查相对链接、JSON、图表、`git diff --check` 和 `npm.cmd run check:docs` 中适用的部分。实施卡运行 `npm.cmd run check`；影响生成目录时先跑 `npm.cmd run knowledge:generate` 并审阅差异。涉及正式构建边界时另跑 `npm.cmd run check:release`，区分原有草稿拒绝与新增失败。交付列出分支、提交、PR、实际命令、未跑项、局限和下一位决定人。临时文件放项目内 `.private/tmp/`，浏览器配置放 `.private/browser/`，均不暂存。常规工作在 Issue/PR 留痕；负责人把任务定为里程碑、迁移或发布时，再更新迭代板和对应 delivery 报告。
