# 项目执行方案：开发工程与知识工程

制定日期：2026-11-25。基线：`trae/work` 与 `origin/main` 同为 `eccc9b5`。本文件是两条工作线的共同纲领；具体规范仍以 [工程方案](engineering-plan.md)、[编辑流程](atlas-workflow.md)、[设计系统](design-system.md) 和 [迭代台账](iteration-board.md) 为准。

## 为什么分成两条线

《碑帖之间》的增长不是单一方向。程序决定知识怎样被组织、呈现和检索；内容决定知识是否准确、系统、可学。把两者混在一条队列里，会出现“内容一扩充就返工界面”或“界面一改版就冻结编辑”的循环。两条线通过 `knowledge/` → `data/index/knowledge-v1.json` 这一个只读接口协作：内容只改 Markdown，程序只消费接口。

| 项目 | 开发工程 | 知识工程 |
| --- | --- | --- |
| 负责 | TRAE | WorkBuddy |
| 工作分支 | `trae/work` | `workbuddy/work` |
| 主要资产 | 程序、接口、网站 | 档案、文章、专题 |
| 核心标准 | 稳定、易用、可维护 | 准确、系统、可学习 |
| 工作性质 | 阶段性迭代 | 长期持续建设 |
| 验收 | 功能与技术验收 | 专业与编辑验收 |

协调人保留优先级、范围、合并与最终验收的决定权。任何一方不得为了迁就现有程序改写知识本身的含义；反之，程序也不为尚未定稿的内容提前造结构。

## 开发工程（D1–D5）

原则：不整体重建架构，不引入没有明确需求的后端、CMS 或搜索服务。现有 React + TypeScript + Vite + Markdown 编译链保留。

| 编号 | 工作包 | 内容 | 优先级 |
| --- | --- | --- | --- |
| D1 | 基础架构维护 | 接口字段梳理、学习内容数据结构、媒体资源结构、草稿与正式分轨、冗余清理 | P0 |
| D2 | 知识展示系统 | 分类检索、别名与简繁检索、作品详情层次、图像放大、版本对照、相关推荐、引文与审核状态 | P0 |
| D3 | 书法学习系统 | 学习入口、专题与路径的通用展示与导航；学习正文由知识端提供，不写进组件 | P1 |
| D4 | 数字人文展示 | 时间轴筛选、馆藏地图联动、人物关系、碑帖流传、风格演变；不做复杂图谱与全历史地理复原 | P2 |
| D5 | 体验与运维 | 移动端、性能、无障碍、国内访问、地图与动画降级、反馈与贡献 | P1（贯穿） |

本轮先做分析与设计（D-001～D-004），接口方案见 [学习内容与媒体接口](learning-interface.md)，作品页方案见 [作品详情页改版](work-page-redesign.md)，仓库风险见 [公开仓库审查](repository-audit.md)。未获批准的接口不进入实现。

## 知识工程（K1–K6）

原则：档案、考证、赏析、教学、专题分层建设。数量目标只用于资源规划，不允许为达标降低审核质量。

| 编号 | 工作包 | 内容 | 优先级 |
| --- | --- | --- | --- |
| K1 | 基础档案 | 作品、实物、书家、地点、来源、事件 | P0 |
| K2 | 资料研究与考证 | 版本辨析、递藏、来源核查、学术异说 | P0 |
| K3 | 书法专业知识 | 书体、技法、结构、风格、审美与历史演变 | P1 |
| K4 | 作品导读与临习 | 作品分析、典型字例、学习重点、临习建议 | P0 |
| K5 | 学习体系 | 基础知识、学习方法、专题研究与学习路径 | P1 |
| K6 | 编辑与审核 | 术语与编辑规范、技术检查、专业审核、批准发布 | P0（贯穿） |

## 五层知识体系

知识不按朝代平铺，而按可学习的深度分层。当前项目主要建成第一、二层；下一阶段重点补第三、四层，第五层长期积累。

1. 基础档案与证据：作品、实物、馆藏、原始文献。
2. 书法历史与研究：书家、版本、流传、历史关系。
3. 作品导读与临习：笔法、结体、章法、读帖与训练。
4. 专题与学习路径：书体学习、风格比较、临创转换。
5. 书法思想与审美：书论、审美判断、传统与现代。

## 协同边界

| 事项 | 开发 | 知识 | 批准 |
| --- | --- | --- | --- |
| 数据模型修改 | 设计实现 | 提出需求 | 协调人 |

| 网站界面 | 负责 | 提出意见 | 协调人验收 |
| 史料录入 | 提供工具与校验 | 负责 | 抽查 |
| 作品导读 | 提供模板与渲染 | 撰写审校 | 专业验收 |
| 学习路径 | 开发功能 | 设计内容 | 协调人审定 |
| 技术发布 | 执行 | 确认内容状态 | 协调人批准 |

冲突时以真实知识需求决定数据结构。新增 `knowledge/` 子目录、字段或内容类型必须由开发端先提供编译与校验支持，知识端不得先行落库。

## 节奏与验收

- 每条线一个小 PR，合并前同步 `origin/main`；CI 必过，评审结论可见。
- 开发线跑 `npm.cmd run check`；改编译器或接口再跑 `npm.cmd run check:reproducible`。
- 知识线改源稿后跑 `npm.cmd run knowledge:compile && npm.cmd run knowledge:generate`，再跑 `npm.cmd run check`。
- 技术检查与专业审核分离。实现者自己的工具审查记为自审，不能代替独立审核。
- 里程碑更新 [迭代台账](iteration-board.md) 并写 `docs/delivery-NNN.md`；普通任务在 Issue/PR 内闭环。
